## 一、设计原则

### 1.1 表前缀规范

| 前缀 | 含义 | 示例 |
|------|------|------|
| `sys_` | 系统管理表（沿用 RuoYi 原生） | `sys_user`, `sys_role`, `sys_menu` |
| `biz_` | 业务表（核心业务模块） | `biz_contract`, `biz_approval`, `biz_customer` |
| `log_` | 日志表（沿用 RuoYi 原生） | `log_login`, `log_operation` |

### 1.2 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 数据库 | 小写下划线 | `sd_publish_scm` |
| 表名 | 小写下划线，前缀区分类型 | `biz_contract`, `sys_user` |
| 列名 | 小写下划线 | `user_name`, `created_at` |
| 主键 | `id` | 统一使用 `id` |
| 外键 | `{表名}_id` | `user_id`, `contract_id` |
| 时间戳 | `{action}_at` | `created_at`, `updated_at` |
| 布尔值 | `is_{描述}` | `is_deleted`, `is_active` |

## 三、系统管理表（复用 RuoYi 原生）

> 以下表结构直接沿用 RuoYi-FastAPI 原生设计，不做任何修改。业务模块开发时通过 DAO 层访问。

### 3.1 用户表 `sys_user`

**沿用 RuoYi 原生结构，新增 `signature` 字段**。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | bigint | PK, 自增 | 用户主键 |
| `user_name` | varchar(30) | NOT NULL, UNIQUE | 登录账号 |
| `nick_name` | varchar(30) | NOT NULL | 用户昵称/姓名 |
| `email` | varchar(100) | | 邮箱 |
| `phonenumber` | varchar(20) | | 手机号 |
| `sex` | char(1) | | 性别：0=男, 1=女, 2=未知 |
| `avatar` | varchar(100) | | 头像 URL |
| `password` | varchar(100) | NOT NULL | 密码（BCrypt 加密） |
| `status` | char(1) | NOT NULL, DEFAULT '0' | 账号状态：0=正常, 1=停用 |
| `del_flag` | char(1) | NOT NULL, DEFAULT '0' | 删除标志：0=存在, 2=删除 |
| `login_ip` | varchar(50) | | 上次登录 IP |
| `login_date` | datetime | | 上次登录时间 |
| `pwd_update_date` | datetime | | 密码最后更新时间 |
| `dept_id` | bigint | FK → sys_dept.id | 所属部门 |
| `signature` | varchar(500) | **新增** | 电子签名（base64 data URI，审批时快照） |
| `create_by` | varchar(64) | | 创建者 |
| `create_time` | datetime | | 创建时间 |
| `update_by` | varchar(64) | | 更新者 |
| `update_time` | datetime | | 更新时间 |
| `remark` | varchar(500) | | 备注 |

> **本系统扩展说明**：
> - RuoYi 原生使用多对多 `sys_user_role` 关联表表达用户与角色的关系，**本系统不做变更**
> - `is_superuser` **不再单独建字段**，superuser 通过「拥有 `role_id=1` 的 `admin` 角色」来表达
> - `approval_role` **不再单独建字段**，审批角色复用 `sys_role` 表，通过 `role_key` 和 `role_sort` 表达

### 3.2 用户-角色关联表 `sys_user_role`

**沿用 RuoYi 原生多对多关联表**。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `user_id` | bigint | PK, FK → sys_user.id | 用户 ID |
| `role_id` | bigint | PK, FK → sys_role.id | 角色 ID |

> **设计说明**：RuoYi 原生支持一个用户拥有多个角色。本系统约定：
> - 用户可同时拥有「业务经办」和「业务复核」等多个角色
> - 审批链判断时，遍历用户的所有角色，匹配 `role_sort` 即可

### 3.3 角色表 `sys_role`

**沿用 RuoYi 原生结构，新增 `role_sort` 用于审批链排序**。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | bigint | PK, 自增 | 角色主键 |
| `role_name` | varchar(30) | NOT NULL | 角色名称（如「业务经办」） |
| `role_key` | varchar(100) | NOT NULL, UNIQUE | 角色标识（如 `business_handler`） |
| `role_sort` | int | NOT NULL, DEFAULT 0 | **审批链顺序**：0=admin(超管), 1=业务经办, 2=业务复核, 3=风控, 4=财务经办, 5=财务复核, 6=供管负责人, 7=投资负责人 |
| `data_scope` | char(1) | NOT NULL, DEFAULT '1' | 数据范围：1=全部, 2=自定义, 3=本部门, 4=本部门及下级, 5=本人 |
| `menu_check_strictly` | tinyint | DEFAULT 1 | 菜单树严格关联 |
| `dept_check_strictly` | tinyint | DEFAULT 1 | 部门树严格关联 |
| `status` | char(1) | NOT NULL, DEFAULT '0' | 状态：0=正常, 1=停用 |
| `del_flag` | char(1) | NOT NULL, DEFAULT '0' | 删除标志 |
| `create_by` | varchar(64) | | 创建者 |
| `create_time` | datetime | | 创建时间 |
| `update_by` | varchar(64) | | 更新者 |
| `update_time` | datetime | | 更新时间 |
| `remark` | varchar(500) | | 备注 |

> **关键设计点**：
> - `role_sort` = 0：超级管理员 `admin`（隐藏，不在 7 级审批链中）
> - `role_sort` = 1-7：7 级审批链角色
> - `role_sort` > 7 或 `role_sort` = NULL：非审批角色（如系统管理员、普通用户等业务角色）
> - `role_key` 作为审批角色的标识字符串（如 `business_handler`），用于业务逻辑判断

## 四、核心业务表

### 4.1 合同主表 `biz_contract`

**核心业务表**，记录合同的全生命周期信息。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | bigint | PK, 自增 | 合同 ID |
| `contract_no` | varchar(50) | NOT NULL, UNIQUE | **合同编号**（当前阶段手动输入） |
| `title` | varchar(200) | NOT NULL | 合同名称 |
| `contract_type` | varchar(20) | NOT NULL | 合同类型：`payment`=业务付款审批单 / `business`=业务审批单 |
| `party_a` | varchar(200) | NOT NULL | **甲方（客户）** |
| `party_b` | varchar(200) | NOT NULL | **乙方（本司）** |
| `amount` | decimal(18,2) | NOT NULL | 合同金额（元） |
| `amount_in_words` | varchar(100) | | 金额大写 |
| `sign_date` | date | | 签订日期 |
| `department` | varchar(100) | | 申请部门 |
| `business_type` | varchar(50) | | 业务类型（如：景区门票、文创产品等） |
| `customer_id` | bigint | FK → biz_customer.id | 关联客户 ID |
| `remark` | text | | 合同备注 |
| `attachments` | json | | 附件列表：`[{name, url}]` |
| `status` | varchar(20) | NOT NULL, DEFAULT 'draft' | 合同状态：`draft`=草稿 / `pending`=审批中 / `approved`=已通过 / `rejected`=已驳回待修改 |
| `current_step` | int | NOT NULL, DEFAULT 0 | 当前审批步骤（0-6）：0=业务经办提交, 1=业务复核, 2=风控审核, 3=财务经办, 4=财务复核, 5=供管负责人, 6=投资负责人 |
| `reject_count` | int | NOT NULL, DEFAULT 0 | 累计驳回次数 |
| `created_by` | bigint | NOT NULL, FK → sys_user.id | 创建人（业务经办） |
| `create_time` | datetime | NOT NULL | 创建时间 |
| `update_by` | varchar(64) | | 更新者 |
| `update_time` | datetime | | 更新时间 |

> **索引设计**：
> - `uk_contract_no`：合同编号唯一约束
> - `idx_status`：按状态查询（审批中心核心索引）
> - `idx_current_step`：按审批步骤查询（待我审批核心索引）
> - `idx_created_by`：按创建人查询（我的合同核心索引）
> - `idx_create_time`：按时间查询

> **状态说明**：
> - `draft`：业务经办创建，未提交审批，可编辑可删除
> - `pending`：已进入 7 级审批链，流转中，不可编辑（超管可介入）
> - `approved`：已通过（终态），不可编辑
> - `rejected`：**已驳回待修改**，可重新提交，保留审批历史

### 4.2 审批记录表 `biz_approval`

记录合同审批的全量历史，用于审计追溯。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | bigint | PK, 自增 | 审批记录 ID |
| `contract_id` | bigint | NOT NULL, FK → biz_contract.id | 关联合同 ID |
| `approver_id` | bigint | FK → sys_user.id | 审批人用户 ID |
| `approver_name` | varchar(50) | | 审批人姓名（冗余，便于查询） |
| `step` | int | NOT NULL | 审批步骤（0-6），记录历史 step 值 |
| `approver_role` | varchar(50) | NOT NULL | 审批时角色标识（如 `business_reviewer`），用于追溯「当时是以什么角色审批的」 |
| `action` | varchar(20) | NOT NULL | 审批动作：`approve`=通过 / `reject`=驳回 |
| `comment` | text | | 审批意见 |
| `reject_reason` | text | | 驳回原因（`action=reject` 时必填） |
| `signature_snapshot` | text | | 审批时电子签名快照（base64 data URI） |
| `approval_ip` | varchar(50) | | 审批操作 IP |
| `approval_time` | datetime | NOT NULL | 审批时间 |
| `create_time` | datetime | NOT NULL | 记录创建时间 |

> **设计说明**：
> - 驳回后重新提交，`contract.status` 变为 `pending`，但 `biz_approval` 中**保留所有历史记录**
> - `step` 字段记录历史 step 值（如被驳回后重新提交，step 会重新从 0 开始，但历史记录的 step 值不变）
> - `approver_role` 记录审批当时的角色（如用户同时有多个角色，审批时用的具体是哪个角色）
> - `action` 一期仅支持 `approve` / `reject`，`withdraw` / `transfer` / `cosign` 作为后续增强

> **索引设计**：
> - `idx_contract_id`：按合同查询审批历史
> - `idx_approver_id`：按审批人查询审批记录
> - `idx_step`：按步骤查询
> - `idx_approval_time`：按时间排序（时间轴展示）

## 五、预置数据

### 5.1 角色预置数据（`sys_role`）

系统初始化时预置 8 个角色：

| `id` | `role_name` | `role_key` | `role_sort` | `data_scope` | 审批链 |
|------|-------------|------------|-------------|--------------|--------|
| 1 | 超级管理员 | `admin` | 0 | 1 | **否（隐藏）** |
| 2 | 业务经办 | `business_handler` | 1 | 5 | Step 0 |
| 3 | 业务复核 | `business_reviewer` | 2 | 4 | Step 1 |
| 4 | 风控审核 | `risk_auditor` | 3 | 1 | Step 2 |
| 5 | 财务经办 | `finance_handler` | 4 | 1 | Step 3 |
| 6 | 财务复核 | `finance_reviewer` | 5 | 1 | Step 4 |
| 7 | 供管公司负责人 | `scm_director` | 6 | 1 | Step 5 |
| 8 | 投资公司负责人 | `invest_director` | 7 | 1 | Step 6 |

> **说明**：
> - `role_id=1` 的 `admin` 为超级管理员，`role_sort=0` 表示**不在审批链中**
> - `role_sort` 的值 1-7 严格对应 7 级审批链的 step 0-6
> - `role_id=1` 的 `admin` 角色在 RuoYi 原生中应配置权限为 `*:*:*`（全部权限）
