> 文档版本：v2.0  
> 创建日期：2026-07-10

## 一、设计背景

### 1.1 核心矛盾

当前系统面临两个不同维度的权限需求：

| 权限类型 | 描述 | 典型系统 |
|----------|------|----------|
| **业务权限** | 谁能操作什么数据 | RuoYi RBAC |
| **审批权限** | 谁在哪个环节可以审批 | 7级审批链（独有） |

两种权限模型在架构上有本质差异：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    RuoYi RBAC 权限模型                              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   用户 ←──属于──→ 角色 ←──拥有──→ 菜单/按钮权限                  │
│                                                                     │
│   特点：                                                           │
│   · 任意用户可分配任意角色                                          │
│   · 角色决定能看到哪些菜单                                          │
│   · 无固定审批顺序                                                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                    7级审批链权限模型                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   合同 ←──按顺序流转──→ 审批环节（Step 0~6）                       │
│                          ↑                                          │
│                          │                                          │
│                    特定角色才能审批                                  │
│                    (业务经办/财务复核/...)                          │
│                                                                     │
│   特点：                                                           │
│   · 审批顺序固定，不可跳过                                           │
│   · 每一步只能由特定角色审批                                         │
│   · 审批人是角色，不是具体用户                                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 设计目标

1. **保持7级审批链的完整性** — 这是核心业务逻辑，不能破坏
2. **复用RuoYi的菜单/按钮权限设计** — 避免重复造轮子
3. **两套模型共存但互不干扰** — 审批链管"谁能审批"，RBAC管"谁能看菜单"

### 2.2 两套模型分工

| 维度 | RBAC角色 | 审批链角色 |
|------|----------|------------|
| **控制什么** | 菜单/按钮/接口 | 审批环节 |
| **判断逻辑** | `用户.角色 ∈ 角色.菜单列表` | `合同.current_step == 用户.角色` |
| **灵活性** | 可自由分配 | 审批顺序固定 |
| **存储位置** | `sys_user.role_id → sys_role → sys_menu` | `合同.current_step` |

```python
# backend/app/core/enums.py

class Role(str, Enum):
    """业务角色 - 用于7级审批链"""
    BUSINESS_HANDLER = "business_handler"      # 业务经办
    BUSINESS_REVIEWER = "business_reviewer"   # 业务复核
    RISK_AUDITOR = "risk_auditor"            # 风控审核
    FINANCE_HANDLER = "finance_handler"       # 财务经办
    FINANCE_REVIEWER = "finance_reviewer"     # 财务复核
    SCM_DIRECTOR = "scm_director"            # 供管公司负责人
    INVEST_DIRECTOR = "invest_director"        # 投资公司负责人


class ApprovalStep:
    """审批环节定义"""
    
    CHAIN = [
        {
            "step": 0,
            "role": Role.BUSINESS_HANDLER,
            "name": "业务经办",
            "description": "创建合同并提交审批",
            "auto_approve": True,  # Step 0 自动完成（提交即审批）
        },
        {
            "step": 1,
            "role": Role.BUSINESS_REVIEWER,
            "name": "业务复核",
            "description": "复核业务内容",
            "auto_approve": False,
        },
        {
            "step": 2,
            "role": Role.RISK_AUDITOR,
            "name": "风控审核",
            "description": "风险控制审核",
            "auto_approve": False,
        },
        {
            "step": 3,
            "role": Role.FINANCE_HANDLER,
            "name": "财务经办",
            "description": "财务数据处理",
            "auto_approve": False,
        },
        {
            "step": 4,
            "role": Role.FINANCE_REVIEWER,
            "name": "财务复核",
            "description": "财务复核确认",
            "auto_approve": False,
        },
        {
            "step": 5,
            "role": Role.SCM_DIRECTOR,
            "name": "供管公司负责人",
            "description": "供应链管理部门审批",
            "auto_approve": False,
        },
        {
            "step": 6,
            "role": Role.INVEST_DIRECTOR,
            "name": "投资公司负责人",
            "description": "最终审批",
            "auto_approve": False,
        },
    ]
    
    @classmethod
    def get_role_at_step(cls, step: int) -> Role:
        """获取某一步骤对应的角色"""
        if 0 <= step < len(cls.CHAIN):
            return cls.CHAIN[step]["role"]
        raise ValueError(f"Invalid step: {step}")
    
    @classmethod
    def is_final_step(cls, step: int) -> bool:
        """判断是否最后一步"""
        return step == len(cls.CHAIN) - 1
```

### 4.3 审批判断逻辑

```python
# backend/app/services/approval_service.py

class ApprovalService:
    """审批服务"""
    
    def can_approve(self, contract: Contract, user: User) -> bool:
        """
        判断用户是否可以审批当前合同
        """
        # 1. 合同必须处于pending状态
        if contract.status != ContractStatus.PENDING:
            return False
        
        # 2. 超级管理员可以审批任意环节
        if user.is_superuser:
            return True
        
        # 3. 普通用户：当前步骤角色必须匹配
        current_step = contract.current_step
        expected_role = ApprovalStep.get_role_at_step(current_step)
        
        return user.role == expected_role.value
    
    def get_pending_contracts(self, user: User) -> list[Contract]:
        """
        获取当前用户待审批的合同列表
        """
        if user.is_superuser:
            # 超管看全部pending
            return self.get_pending_contracts_query().all()
        
        # 普通用户：根据角色筛选
        expected_role = user.role  # 用户当前角色
        
        # 找到该角色对应的步骤
        step = None
        for i, item in enumerate(ApprovalStep.CHAIN):
            if item["role"].value == expected_role:
                step = i
                break
        
        if step is None:
            return []
        
        # 查询当前步骤且状态为pending的合同
        return self.get_pending_contracts_query().filter(
            Contract.current_step == step
        ).all()
```

```python
# backend/app/api/deps.py

async def get_current_user(
    request: Request,
    db: Session = Depends(get_db)
) -> User:
    """获取当前用户，同时包含RBAC权限信息"""
    
    # 1. JWT解析
    token = request.headers.get("Authorization", "").replace("Bearer ", "")
    payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    user_id = payload.get("sub")
    
    # 2. 查询用户（含RBAC角色信息）
    user = db.query(User).filter(User.id == user_id).first()
    if not user:
        raise HTTPException(401, "用户不存在")
    
    # 3. 查询用户菜单权限
    menus = db.query(Menu).join(RoleMenu).join(Role).filter(
        Role.id == user.rbac_role_id
    ).all()
    
    # 4. 存储用户信息和菜单权限
    user.menu_permissions = [m.path for m in menus]
    user.can_approve_contracts = _get_can_approve_roles(user)  # 审批角色判断
    
    return user
```

### 6.1 超级管理员

超级管理员拥有最高权限：

| 权限 | 说明 |
|------|------|
| 菜单权限 | 全部可见 |
| 审批权限 | 可审批任意环节 |
| 用户管理 | 可管理所有用户 |
| 系统配置 | 可修改系统参数 |
| 数据导出 | 可导出全部数据 |

### 6.2 代理审批

当审批人因故无法审批时：

```
场景：财务经办A请假一周，但有3个合同等待财务经办审批

方案：
1. A联系超管，说明情况
2. 超管将A的"审批权限"临时转给B
3. B可以审批A待处理的合同
4. A回来后，超管恢复A的权限
```

### 6.3 会签场景

```
场景：某些重要合同需要财务经理由2人以上同时审批

实现：
1. 在ApprovalStep.CHAIN中定义会签步骤
2. 会签步骤需要N个人审批
3. 记录会签人员
4. 全部会签通过后，才能进入下一步
```

## 七、实施建议

### 7.1 开发顺序

```
阶段一：基础RBAC权限
├── 用户登录认证
├── 菜单权限控制
├── 按钮权限控制
└── 角色管理（超管操作）

阶段二：7级审批链
├── 审批链核心逻辑
├── 审批通过/驳回
├── 审批记录（含签章）
├── 待我审批列表
└── 审批历史查看

阶段三：审批增强
├── 撤回功能
├── 转交功能
├── 加签功能
└── 审批超时提醒
```

### 7.2 测试要点

| 测试场景 | 预期结果 |
|----------|----------|
| 业务经办提交合同 | Step 0自动完成，进入Step 1 |
| 业务复核人审批通过 | 进入Step 2 |
| 非当前审批角色尝试审批 | 返回403禁止 |
| 超管审批任意环节 | 审批通过 |
| 驳回后重新提交 | 保留历史审批记录 |
| 撤回合同 | 回到草稿状态 |
| 转交审批 | 被转交人可以审批 |
