# 权限模型设计文档

> 文档版本：v3.0  
> 更新日期：2026-07-10  
> 文档定位：以 RuoYi-FastAPI 原生 RBAC 为基础，融合 7 级审批链的完整权限方案

## 〇、修订说明（v2.0 → v3.0）

| 修订点 | 旧设计 | 新设计 |
|--------|--------|--------|
| 基础框架 | 自定义两套模型独立运行 | **直接复用 RuoYi RBAC**，`sys_role.role_key` 作为审批角色标识 |
| 用户表 | 自定义 `approval_role` + `rbac_role_id` 字段 | 沿用 RuoYi 原生 `sys_user` + `sys_user_role` 关联表 |
| superuser 表达 | 单独 `is_superuser` 字段 | **RuoYi 原生方案**：创建 `admin` 角色（`role_id=1`），其权限字符串为 `*:*:*` 通配 |
| 7 级审批链实现 | 硬编码枚举 | 复用 RuoYi `sys_role`，通过 `role_key`（如 `business_handler`）匹配 |
| 审批链配置 | 写死 | 通过「`sys_role` 排序 + 配置表 `biz_approval_step`」配置化 |
| 数据范围 | 自定义 | 直接使用 RuoYi `sys_role.data_scope`（1-5 五级） |
| 驳回后状态 | 模糊（"合同终止"） | 明确为 `rejected`（已驳回待修改），可重新提交，**不是终止态** |
| 转交/加签/会签 | 一期实现 | **一期不支持**（v1 现状），标记为后续增强项 |

**核心原则**：能复用 RuoYi 的就复用 RuoYi，v1 demo 仅作为业务规则和 UI 交互的参考。

## 一、设计背景与目标

### 1.1 业务诉求

本系统是「智能运营平台」，服务于山东出版集团供应链管理业务。核心场景包含：

- **7 级固定审批链**：业务经办 → 业务复核 → 风控审核 → 财务经办 → 财务复核 → 供管公司负责人 → 投资公司负责人
- **多角色用户**：业务人员、审批人员、财务人员、领导、超管
- **精细权限**：菜单可见性、按钮可见性、数据行级可见性

### 1.2 设计原则

1. **RuoYi 优先**：用户、角色、菜单、按钮、字典、日志等基础能力**全部复用** RuoYi-FastAPI
2. **7 级审批链作为业务模块**：不破坏 RuoYi RBAC，作为「合同审批业务模块」的一部分
3. **审批角色 = RBAC 角色**：用 RuoYi `sys_role` 表示 7 级审批角色，`role_key` 即为审批角色值
4. **superuser = 特殊角色**：`admin` 角色（`role_id=1`）拥有 `*:*:*` 通配权限，不属于 7 级审批链

### 1.3 核心概念对齐

| 概念 | 含义 | 涉及表 |
|------|------|--------|
| **用户 (User)** | 系统操作者 | `sys_user` |
| **角色 (Role)** | 一组权限的集合（RuoYi 原生） | `sys_role` |
| **审批角色** | 7 级审批链中的某一环，**复用 `sys_role`** | `sys_role`（`role_key` 字段） |
| **菜单权限** | 控制页面和按钮可见性 | `sys_menu` + `sys_role_menu` |
| **数据权限** | RuoYi 五级数据范围 | `sys_role.data_scope` |
| **超级管理员 (superuser)** | 隐藏系统角色，绕过权限 | `sys_role.role_id=1`，权限 `*:*:*` |

## 二、RuoYi 原生权限模型（基础层）

### 2.1 核心表结构

直接沿用 RuoYi-FastAPI 自带的表结构，**不做修改**：

```
sys_user           用户表
sys_role           角色表
sys_user_role      用户-角色关联表（多对多）
sys_menu           菜单（含按钮）表
sys_role_menu      角色-菜单关联表
sys_dept           部门表
```

### 2.2 关键字段含义

#### `sys_user`（用户）

| 字段 | 类型 | 说明 |
|------|------|------|
| `user_id` | bigint PK | 用户主键 |
| `user_name` | varchar(30) | 登录账号 |
| `nick_name` | varchar(30) | 昵称/姓名 |

| 字段 | 类型 | 说明 |

| `role_id` | bigint | 角色 ID（联合主键） |

## 三、7 级审批链与 RuoYi 融合方案

### 3.1 核心设计思想

**审批角色不是新建一张表，而是直接复用 RuoYi 的 `sys_role`，通过 `role_key` 表达。**

```
合同.current_step (int 0-6)
        │
        ▼
sys_role 表中 role_sort = current_step + 1 的记录
        │
        ▼
该 role 的 role_key（如 business_reviewer）
        │
        ▼
匹配 sys_user_role 中 user_id 对应的 role_id
        │
        ▼
判断「该用户是否拥有该审批角色」
```

### 3.2 审批链预置数据（初始化脚本）

在系统初始化时，向 `sys_role` 写入 8 条记录：

| `role_id` | `role_name` | `role_key` | `role_sort` | `data_scope` | 菜单权限 |
|-----------|-------------|------------|-------------|--------------|----------|
| 1 | 超级管理员 | `admin` | 0 | 1（全部） | 全部菜单 + `*:*:*` |
| 2 | 业务经办 | `business_handler` | 1 | 5（本人） | 合同管理（自己）、客户管理（只读） |
| 3 | 业务复核 | `business_reviewer` | 2 | 4（本部门及下级） | 合同管理、审批中心 |
| 4 | 风控审核 | `risk_auditor` | 3 | 1（全部） | 合同管理、审批中心 |
| 5 | 财务经办 | `finance_handler` | 4 | 1（全部） | 合同管理、审批中心、财务管理、发票管理 |
| 6 | 财务复核 | `finance_reviewer` | 5 | 1（全部） | 合同管理、审批中心、财务管理、发票管理 |
| 7 | 供管公司负责人 | `scm_director` | 6 | 1（全部） | 合同管理、审批中心、经营数据 |
| 8 | 投资公司负责人 | `invest_director` | 7 | 1（全部） | 合同管理、审批中心、经营数据 |

> **关键约定**：
> - `role_id=1` 的 `admin` 角色**不属于 7 级审批链**（`role_sort=0`），是隐藏系统角色
> - 审批链中 7 个角色的 `role_sort` 分别为 1-7，**严格对应 7 级审批顺序**
> - 所有 7 级审批角色的 `perms` 字段均包含 `*:*:*` 是**错误**的，会绕过权限，应只授予具体业务菜单

### 3.3 用户-审批角色映射

通过 `sys_user_role` 多对多关联表实现：

```
sys_user
   │
   │ user_id
   │
   ▼
sys_user_role
   │
   │ role_id
   │
   ▼
sys_role
   │
   │ role_sort ∈ [1, 7]
   │
   ▼
该用户在 7 级审批链中的角色
```

**业务约定**：

- 一个用户**可以拥有多个角色**（如：业务经办 + 业务复核，可同时执行两级审批）
- 审批链判断时，**遍历用户的所有角色**，只要其中有 `role_sort = current_step + 1` 的角色，即可审批
- 实务中演示数据为**一人一角色**，简化演示

### 3.4 superuser 判定逻辑

RuoYi 原生方案：

```python
def is_superuser(user: SysUser, user_roles: list[SysRole]) -> bool:
    """
    判定逻辑：
    - RuoYi 原生：拥有 role_id=1 的 admin 角色即为超管
    - 通过 user_roles 中是否存在 role_id=1 来判断
    - 不需要在 sys_user 上加额外字段
    """
    return any(role.role_id == 1 for role in user_roles)
```

**超管在审批链中的特殊权限**：

- 菜单：拥有 `*:*:*` 通配，全部可见
- 审批：可审批**任意环节**的合同（前端审批中心展示全部 pending 合同）
- 业务：可绕过部门/本人数据范围限制
- **不参与审批链计数**（不是 7 级审批链中的第 8 级）

### 3.5 7 级审批链判定流程

#### 步骤 1：用户登录，组装 CurrentUser

RuoYi 原生 `login_service.get_current_user` 已实现：

```python
# 来自 module_admin/service/login_service.py（伪代码简述）
async def get_current_user(request, token, query_db):
    # 1. JWT 解析，获取 user_id
    payload = jwt.decode(token, ...)
    user_id = payload.get('user_id')
    
    # 2. 查询用户
    user = await UserDao.get_user_by_id(query_db, user_id)
    
    # 3. 查询用户角色列表
    user_roles = await UserDao.get_user_roles_by_id(query_db, user_id)
    # 返回 [{role_id, role_key, role_name, role_sort, data_scope, ...}, ...]
    
    # 4. 计算权限列表
    if any(r.role_id == 1 for r in user_roles):
        permissions = ['*:*:*']  # superuser
    else:
        permissions = await UserDao.get_user_permissions(query_db, user_id)
    
    # 5. 组装 CurrentUserModel
    return CurrentUserModel(
        user=user,
        roles=user_roles,
        permissions=permissions,
        is_superuser=any(r.role_id == 1 for r in user_roles),
    )
```

#### 步骤 2：合同审批权限判断

```python
# 业务模块新增：biz/approval/service.py
from module_admin.entity.do.user_do import SysUser
from module_admin.entity.do.role_do import SysRole
from module_admin.service.login_service import LoginService

class ApprovalService:
    """审批权限判断服务（与 RuoYi 解耦，仅消费 CurrentUser）"""
    
    def can_approve_contract(
        self, 
        contract: BizContract, 
        current_user: CurrentUserModel
    ) -> bool:
        """
        判断当前用户能否审批给定合同
        """
        # 1. 合同必须处于 pending 状态
        if contract.status != ContractStatus.PENDING:
            return False
        
        # 2. superuser 可审批任意环节
        if current_user.is_superuser:
            return True
        
        # 3. 检查用户角色中是否有「当前步骤对应的审批角色」
        expected_role_sort = contract.current_step + 1  # 步骤 0 → role_sort=1
        
        user_approval_roles = [
            r for r in current_user.roles 
            if 1 <= r.role_sort <= 7
        ]
        
        return any(r.role_sort == expected_role_sort for r in user_approval_roles)
    
    def get_pending_contracts_for_user(
        self, 
        db: AsyncSession, 
        current_user: CurrentUserModel
    ) -> list[BizContract]:
        """
        获取当前用户待审批的合同列表
        """
        # superuser 看全部 pending
        if current_user.is_superuser:
            return await BizContractDao.get_pending_contracts(db)
        
        # 普通用户：根据角色筛选
        user_role_sorts = [
            r.role_sort for r in current_user.roles 
            if 1 <= r.role_sort <= 7
        ]
        
        if not user_role_sorts:
            return []
        
        # 合同 current_step + 1 == role_sort
        # 即: current_step IN [role_sort - 1 for role_sort in user_role_sorts]
        target_steps = [rs - 1 for rs in user_role_sorts]
        
        return await BizContractDao.get_pending_contracts_by_steps(
            db, target_steps
        )
```

#### 步骤 3：审批操作（通过/驳回）

```python
async def approve_contract(
    db: AsyncSession,
    contract_id: int,
    current_user: CurrentUserModel,
    comment: str = None
):
    contract = await BizContractDao.get_by_id(db, contract_id)
    
    # 1. 权限校验
    if not ApprovalService().can_approve_contract(contract, current_user):
        raise PermissionException("当前用户无权审批此合同")
    
    # 2. 业务规则：是否最后一步
    if contract.current_step == 6:  # 7 级链的 step 索引 0-6
        # 最终审批通过 → 合同归档
        contract.status = ContractStatus.APPROVED
        contract.current_step = 6  # 保持终态
    else:
        # 推进到下一步
        contract.current_step += 1
    
    # 3. 记录审批历史（含电子签名快照）
    approval = BizApproval(
        contract_id=contract_id,
        approver_id=current_user.user.user_id,
        step=contract.current_step,
        approver_role=next(
            r.role_key for r in current_user.roles 
            if r.role_sort == contract.current_step + 1
        ),
        action='approve',
        comment=comment,
        signature_snapshot=current_user.user.signature,  # 电子签章
    )
    db.add(approval)
    await db.commit()
```

## 四、7 级审批链配置（数据化）

### 4.1 配置表（可选）

如果需要可视化配置审批链（业务类型不同，审批链不同），可新增配置表：

```sql
CREATE TABLE `biz_approval_step` (
    `id` INT PRIMARY KEY AUTO_INCREMENT,
    `contract_type` VARCHAR(32) NOT NULL COMMENT '合同类型：业务付款审批单/业务审批单',
    `step_order` INT NOT NULL COMMENT '步骤序号 0-6',
    `role_id` BIGINT NOT NULL COMMENT '审批角色（关联 sys_role）',
    `step_name` VARCHAR(50) NOT NULL COMMENT '步骤名称',
    `is_required` TINYINT DEFAULT 1 COMMENT '是否必经',
    `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (`role_id`) REFERENCES `sys_role`(`role_id`),
    UNIQUE KEY `uk_type_step` (`contract_type`, `step_order`)
);
```

**本期简化**：

- 7 级审批链是**固定配置**，不提供可视化配置界面
- 直接在 `sys_role.role_sort` 字段中体现顺序即可
- 配置表 `biz_approval_step` 作为**未来扩展**（如：业务付款审批单可少于 7 级）

### 4.2 业务合同类型

| 合同类型 | 审批链 | 备注 |
|----------|--------|------|
| 业务付款审批单 | 7 级链 | 全流程 |
| 业务审批单 | 7 级链 | 全流程 |
| 内部审批单 | 后续扩展 | 可少于 7 级 |

> 本期两种合同类型均走 7 级链。

## 五、状态机与驳回语义

### 5.1 合同状态定义

```python
class ContractStatus(str, Enum):
    DRAFT = "draft"            # 草稿（业务经办创建后未提交）
    PENDING = "pending"        # 审批中
    APPROVED = "approved"      # 已通过（终态）
    REJECTED = "rejected"      # 已驳回（**可重新提交**）
    WITHDRAWN = "withdrawn"    # 已撤回（**一期不支持**）
    CLOSED = "closed"          # 已关闭（**一期不支持**）
```

### 5.2 状态流转

```
       ┌──────────────┐
       │     DRAFT     │  业务经办创建，未提交
       └──────┬───────┘
              │ 提交审批
              ▼
       ┌──────────────┐
       │   PENDING     │  7 级链流转中
       └──────┬───────┘
              │
   ┌──────────┼──────────┬──────────────┐
   │ 通过     │ 驳回     │ 终态通过      │
   ▼          ▼          ▼              │
[下一步]   ┌──────────────┐  ┌──────────────┐
   ...     │  REJECTED    │  │  APPROVED    │
           └──────┬───────┘  └──────────────┘
                  │ 业务经办修改后重新提交
                  └──────► PENDING
```

### 5.3 驳回语义（明确）

> **决策记录（ADR-D03）**：`rejected` 状态语义固定为「**已驳回待修改**」，不是草稿，不是终止态。

| 维度 | 明确规则 |
|------|----------|
| 状态名 | `rejected`（已驳回待修改） |
| 是否可编辑 | ✅ 可编辑（仅业务经办可改，且仅自己创建的合同） |
| 是否可删除 | ✅ 可删除（仅草稿/已驳回状态可删，v1 当前实现） |
| 是否可重新提交 | ✅ 可重新提交，重新进入 PENDING，从第 1 级开始 |
| 审批历史 | 保留所有历史审批记录（含驳回记录） |
| 当前步骤 | 驳回时 `current_step` 保持不变，重新提交后从 step 0 开始 |
| 是否终态 | ❌ **不是终态**，仅 `APPROVED` 是终态 |

### 5.4 撤回、加签、转交、会签（本期不支持）

| 功能 | 状态 | 备注 |
|------|------|------|
| **撤回** | 一期不支持 | v1 demo 标记了但未实现实际逻辑 |
| **加签** | 一期不支持 | 需要扩展审批步骤表 |
| **转交** | 一期不支持 | 需要新增转交记录表 |
| **会签** | 一期不支持 | 需要多审批人关联表 |
| **审批时限** | 一期不支持 | 需要定时任务 + 消息提醒 |

> **决策（ADR-D08）**：v1 demo 现状仅支持「通过 / 驳回 / 重新提交」三种动作，一期不实现其他增强功能。

### 8.2 前端路由守卫（参考 v1 + RuoYi）

```javascript
// router/guard.js
import { useUserStore } from '@/store/modules/user'

router.beforeEach((to, from, next) => {
  const userStore = useUserStore()
  const permissions = userStore.permissions || []
  
  // superuser 通配
  if (permissions.includes('*:*:*')) {
    return next()
  }
  
  // 菜单权限校验
  if (to.meta.perms) {
    const required = Array.isArray(to.meta.perms) ? to.meta.perms : [to.meta.perms]
    const hasPerm = required.some(p => permissions.includes(p))
    if (!hasPerm) {
      ElMessage.error('无访问权限')
      return next('/403')
    }
  }
  
  next()
})
```

## 九、特殊场景与边界

### 9.1 superuser 的双面性

| 场景 | superuser 行为 | 设计理由 |
|------|----------------|----------|
| 登录 | 正常登录 | RuoYi 原生 |
| 菜单 | 全部可见 | `*:*:*` 通配 |
| 审批中心 | 展示**全部** pending 合同 | 紧急审批介入 |
| 点击"通过" | 可审批**任意 step** 的合同 | `is_superuser=True` 时 `can_approve_contract` 直接返回 True |
| 业务数据 | 可见全部（`data_scope=1`） | RuoYi 原生 |
| 系统管理 | 全部权限 | `*:*:*` |
| 是否算 7 级审批链 | **不算** | `admin.role_sort=0`，不计入审批链计数 |

### 9.2 同一用户多角色

**场景**：用户 A 同时拥有「业务经办」和「业务复核」两个角色。

**处理**：

- RuoYi 原生支持多角色，`sys_user_role` 中两条记录
- 业务经办：可创建合同（`role_sort=1`）
- 业务复核：可审批 step 0 的合同（`role_sort=2`）
- 审批中心展示：同时看到「待我审批」（业务复核）和「我的申请」（业务经办）
- **无冲突**：不同 step 走不同角色，按 `role_sort` 区分

### 9.3 业务经办 = 合同创建人

**约定**：

- 业务经办创建合同时，`biz_contract.created_by` 记录 `user_id`
- 业务经办修改合同时，仅 `created_by == current_user.user.user_id` 时可改
- 业务经办删除合同时，仅 `created_by == current_user.user.user_id` 且 `status IN (DRAFT, REJECTED)` 时可删

### 9.4 审批通过/驳回权限双重校验

```python
# 双重保险：
# 1. 接口级：RuoYi UserInterfaceAuthDependency('approval:approve') 控制按钮可见性
# 2. 业务级：ApprovalService.can_approve_contract() 校验合同步骤与用户角色

@contract_controller.post(
    '/approve/{contract_id}',
    summary='审批通过',
    dependencies=[UserInterfaceAuthDependency('approval:approve')],
)
async def approve_contract(
    contract_id: int,
    current_user: CurrentUserModel = Depends(LoginService.get_current_user),
    db: AsyncSession = Depends(get_db),
):
    contract = await BizContractDao.get_by_id(db, contract_id)
    
    # 业务级校验
    if not ApprovalService().can_approve_contract(contract, current_user):
        raise PermissionException("您不是当前步骤的审批人")
    
    # 业务处理
    ...
```

### 9.5 审批历史追溯

`biz_approval` 表记录**全部历史**，包括：

- 每次审批动作（approve / reject）
- 审批人当时的角色（`approver_role`）
- 审批时间、意见、电子签名快照
- 驳回后重新提交，**历史保留**，可在审批时间轴查看

## 十一、与 v1 demo 的差异

| 维度 | v1 demo | 重构后 |
|------|---------|--------|
| 基础框架 | 自建 FastAPI 单体 | **RuoYi-FastAPI** 模块化架构 |

| 审批链 | 硬编码 | 复用 `sys_role.role_sort` 表达 |
| superuser | `is_superuser` 字段 | RuoYi 原生 `admin` 角色（`role_id=1`） |

| 审批历史 | 保留 | 保留（含签章） |
| 业务模块 | 单体 | RuoYi module_admin 风格模块化 |
